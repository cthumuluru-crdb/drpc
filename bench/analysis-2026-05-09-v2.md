### How compression was disabled (gRPC cluster only)

```bash
roachprod start chandrathumuluru-c9c2fcda-grpc2:1-5 \
  -e COCKROACH_ENABLE_RPC_COMPRESSION=false
```

The flag is defined in `pkg/rpc/settings.go`:
```go
var enableRPCCompression = envutil.EnvOrDefaultBool("COCKROACH_ENABLE_RPC_COMPRESSION", true)
```
No code changes were required. Setting the env var to `false` disables Snappy on all outgoing
gRPC RPCs from those nodes. Verified at runtime via `/proc/<pid>/environ`.

## Methodology & Caveats

- **SSH timeout**: Both workload processes (`roachprod run`) disconnected due to SSH keepalive
  timeout at ~6032s elapsed (gRPC) and ~6473s (DRPC). The CRDB nodes (1-5) stayed running.
- **No final histogram JSON**: The workload process was killed before writing the final
  `--histograms` file. All workload latency data is from per-second streaming stdout.
- **Latency window**: Uses seconds 3000–5000 (50–83 min elapsed), well past the 5-min ramp
  and before late-run compaction spikes that affected both clusters.
- **CRDB service metrics**: Live Prometheus scrape from `/_status/vars` on node 1 (all 5
  nodes still running at time of scrape, ~3.5h after benchmark start).
- **Periodic hardware metrics**: 7 samples collected every 15 minutes by a background monitor;
  samples 2–7 (13:58–15:17 UTC) used for steady-state averages; sample 1 excluded (caught
  gRPC cluster mid-ramp); sample 8 excluded (post-run).
- **Network bytes**: Normalized by node uptime (14,523s gRPC / 14,558s DRPC) for fair comparison.

### Go runtime summary

| Metric | gRPC | DRPC | Delta | Severity |
|--------|------|------|-------|----------|
| Goroutines / node | 1,981 | 3,187 | **+61%** | WARNING |
| Runnable goroutines / CPU | 2.31 | 3.56 | **+54%** | WARNING |
| GC pause rate (ms/15min) | 34.1 | 35.1 | +3% | INFO |
| GC pause % | ~0.0% | ~0.0% | neutral | INFO |

**Root cause of latency regression:**
DRPC maintains one goroutine per active RPC stream (vs gRPC's multiplexed HTTP/2 streams on
fewer goroutines). At 2500 TPCC warehouses with ~2500 concurrent workers per 5 nodes, each
node handles ~500 concurrent SQL sessions. DRPC's model results in ~1,200 more goroutines
per node. On an 8-vCPU ARM core at 82% CPU utilization, the Go scheduler (GOMAXPROCS=8) must
context-switch between 3,187 goroutines vs 1,981, increasing scheduling latency. This is
visible as **54% higher runnable-goroutines-per-CPU**, which directly causes the 22–98%
workload latency increase.

At 500 warehouses (previous run, ~40% CPU), the goroutine overhead was hidden by available
CPU headroom. At 2500 warehouses (82% CPU), the scheduler is CPU-constrained and the overhead
becomes the dominant latency factor.

consume significantly less network bandwidth, widening this gap further in gRPC's favor.

### Conclusion

At **2500 warehouses on 8-vCPU ARM nodes at ~82% CPU**, moving from gRPC to DRPC:

- **Maintains throughput** (tpmC within 0.2%) — DRPC is safe from a correctness standpoint.
- **Regresses latency by 23–98%** at p50–p99 across all TPCC transaction types. This is the
  dominant finding and makes DRPC unsuitable for latency-sensitive workloads at this load level.
- **Improves inter-node RPC RTT by 20%** (5.21ms vs 6.51ms) — DRPC's lighter framing is
  measurably faster at the protocol level, but this advantage is overwhelmed by goroutine
  scheduling overhead at high concurrency.
- **Increases goroutine count by 61%** and scheduler pressure by 54%, which is the root cause
  of the latency regression.
- **Uses 4.9% more memory** and **6.2% more network bandwidth** per node.

### Recommendation

The latency regression is load-dependent: at 500 warehouses (40% CPU) DRPC showed parity or
slight improvement; at 2500 warehouses (82% CPU) latency degrades by 23–98%. The threshold
appears to be somewhere between 40% and 82% CPU where goroutine scheduling contention starts
to dominate. Before enabling `--use-new-rpc` in production, the DRPC goroutine model should
be profiled and compared at 60–75% CPU utilization to find the crossover point.

The 340× increase in `sql_distsql_select_count` on DRPC also requires investigation — if
DRPC is altering query routing or range lease placement, it could have correctness implications
beyond performance.
